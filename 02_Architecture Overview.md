## Часть 1. Основы RAG и общая архитектура

### 1. Назначение документа

Настоящий документ описывает архитектурные основы технологии Retrieval-Augmented Generation (RAG), используемой в проекте Enterprise Knowledge Assistant. Цель документа — объяснить, каким образом система получает знания из корпоративных документов, почему она не требует переобучения модели при обновлении информации и как обеспечивается генерация ответов на основе актуального корпоративного контекста.[reference:0]

Данный документ является первым из трех документов серии RAG Architecture & Data Flow и посвящен концепции RAG и общей архитектуре решения.[reference:1]

### 2. Что такое RAG

Retrieval-Augmented Generation (RAG) — это архитектурный подход, при котором языковая модель (LLM) формирует ответ не только на основе своих внутренних знаний, но и на основе дополнительного контекста, извлеченного из внешнего источника данных.[reference:2]

В проекте таким источником являются корпоративные документы:
- регламенты командировок;
- регламенты закупок;
- внутренние политики;
- инструкции компании.

Именно эти документы являются источником истины, а не знания, встроенные в модель.[reference:3]

### 3. Почему одного LLM недостаточно

Большие языковые модели обладают широкими знаниями, однако для корпоративных систем этого недостаточно. Основные ограничения LLM:
- модель не знает внутренних регламентов конкретной компании;
- знания модели могут быть устаревшими;
- модель может генерировать правдоподобные, но неверные ответы (галлюцинации);
- обновление корпоративных правил потребовало бы повторного обучения модели, что практически невозможно.[reference:4]

Поэтому архитектура корпоративных AI-систем строится по принципу: **Документы хранятся отдельно, а модель получает только нужный фрагмент информации во время обработки запроса.**[reference:5]

### 4. Архитектурная идея RAG

Основная идея RAG заключается в разделении ответственности между двумя компонентами:

| Компонент | Ответственность |
|-----------|-----------------|
| Knowledge Base | Хранение корпоративных знаний |
| LLM | Анализ вопроса и генерация ответа |

Таким образом:
- корпоративные знания не находятся внутри модели;
- модель не является владельцем информации;
- актуальность данных обеспечивается обновлением документов, а не переобучением модели.[reference:6]

### 5. Общая архитектура RAG

На концептуальном уровне поток обработки выглядит следующим образом:
Корпоративный документ
↓
Обработка документа (Ingestion)
↓
Разбиение на фрагменты (Chunking)
↓
Создание Embeddings
↓
Индексация
↓
Knowledge Base готова

## Часть 2. Ingestion, Chunking, Embeddings и Retrieval

### 1. Назначение документа

Настоящий документ описывает внутренний процесс подготовки корпоративных документов к поиску и механизм извлечения релевантной информации в архитектуре Retrieval-Augmented Generation (RAG). Цель документа — показать, каким образом обычный PDF-документ превращается в структуру, пригодную для быстрого семантического поиска.[reference:8]

### 2. Общая схема обработки документа

После загрузки документа в систему происходит не простое сохранение файла, а последовательность специализированных этапов обработки.[reference:9]

PDF / DOCX / TXT / MD
↓
Извлечение текста
↓
Очистка и нормализация
↓
Разбиение на Chunk'и
↓
Создание Embeddings
↓
Индексация
↓
Knowledge Base готова

После этого документ становится доступным для поиска по смыслу.[reference:11]

### 3. Ingestion Pipeline

**Назначение:** Ingestion Pipeline — это процесс подготовки документа к использованию системой RAG. Важно понимать: **На данном этапе LLM еще не участвует.** Обработка полностью выполняется системой индексации.[reference:12]

**Основные этапы:**

#### 3.1. Загрузка документа
Пользователь загружает документ. В проекте:
- Reglament_Komandirovki.pdf
- Reglament_Zakupok.pdf[reference:13]

#### 3.2. Извлечение текста
Система извлекает текстовое содержимое документа. Например:
> "2.2 Гостиница: Лимит составляет 7000 рублей для РФ, 150 USD для зарубежных командировок."[reference:14]

Если документ является изображением (скан без текстового слоя), потребуется OCR. В рамках MVP мы будем использовать документы с корректным текстовым слоем.[reference:15]

#### 3.3. Очистка текста
Перед индексацией удаляются элементы, не несущие смысловой нагрузки:
- лишние переносы строк;
- повторяющиеся пробелы;
- служебные символы;
- колонтитулы и номера страниц (если возможно).

После очистки текст становится более пригодным для дальнейшей обработки.[reference:16]

### 4. Chunking

**Что такое Chunk:** Chunk — это небольшой логически завершенный фрагмент документа. Именно такие фрагменты участвуют в поиске. LLM никогда не работает со всем документом целиком.[reference:17]

**Почему нельзя использовать весь PDF:** Предположим, документ содержит 80 страниц. Если передавать весь документ модели:
- возрастет стоимость обработки;
- увеличится время ответа;
- часть информации может не поместиться в контекстное окно модели.[reference:18]

### 5. Embeddings и векторный поиск

Каждый Chunk преобразуется в векторное представление (Embedding) — числовой массив, который отражает смысл фрагмента. Векторы семантически близких текстов находятся рядом в многомерном пространстве.

При поиске система:
1. Преобразует вопрос пользователя в вектор.
2. Находит в векторной базе Top-K наиболее семантически близких Chunk'ов.
3. Возвращает эти фрагменты для формирования ответа.

## Часть 3. Prompt Assembly, Generation, Hallucinations и реализация в Dify

### 1. Назначение документа

Настоящий документ завершает описание архитектуры RAG и посвящен этапам формирования запроса к LLM, генерации ответа, причинам возникновения галлюцинаций и связи архитектурных концепций с практической реализацией в Dify.[reference:19]

После изучения всех трех частей читатель должен понимать полный жизненный цикл пользовательского запроса: от загрузки документа в Knowledge Base до формирования финального ответа.[reference:20]

### 2. Полный жизненный цикл запроса

Объединим все ранее рассмотренные этапы в единую схему:
Загрузка документа
↓
Ingestion Pipeline
↓
Chunking
↓
Embeddings
↓
Knowledge Base
══════════════════════════════════════════
Пользовательский вопрос
↓
Embedding пользовательского вопроса
↓
Similarity Search (Top-K)
↓
Найденные фрагменты документов
↓
Prompt Assembly
↓
LLM
↓
Ответ пользователю


### 3. Prompt Assembly

Это один из самых важных этапов работы RAG. LLM никогда не получает только вопрос пользователя. Перед отправкой запроса система собирает единый Prompt из нескольких частей.[reference:22]

Общий принцип выглядит следующим образом:

System Prompt + Retrieved Context + Conversation History + User Question
↓
LLM


Каждый элемент выполняет собственную функцию.[reference:24]

### 4. System Prompt

System Prompt определяет поведение AI. В проекте он содержит такие правила:
- отвечать только по корпоративным документам;
- не придумывать информацию;
- сообщать об отсутствии данных;
- соблюдать деловой стиль общения;
- не отвечать на вопросы вне области компетенции.[reference:25]

System Prompt является постоянной частью каждого запроса.[reference:26]

### 5. Retrieved Context

Это фрагменты документов, найденные системой Retrieval. Например:
> Документ: Reglament_Komandirovki.pdf
> Раздел 2.2
> Лимит гостиницы: 150 USD

Именно этот текст становится источником знаний для модели.[reference:27]

### 6. Conversation History

Для сохранения контекста диалога система может добавлять предыдущие сообщения пользователя и ответы AI.

Пример:
> Пользователь: Какие суточные?
> AI: 1500 рублей.
> Пользователь: А для зарубежной поездки?

Без истории диалога второй вопрос был бы неоднозначным.[reference:28]

### 7. User Question

Последняя часть Prompt — текущий вопрос пользователя. Например:
> Можно ли забронировать гостиницу дороже установленного лимита?[reference:29]

## Часть 4. Архитектура Car Booking Chatbot

### 1. Общая картина

Система — единый Dify Chatflow, обслуживающий два логически независимых сценария внутри одного диалога:

- **Regulation** — RAG поверх базы знаний по регламентам командировок и отпусков, только чтение.
- **Booking** — транзакционная подсистема бронирования автомобилей: поиск доступности, бронирование, просмотр своих броней, отмена. Работает через Supabase (Postgres) как источник истины, доступ — исключительно через RPC-функции.

Граница между подсистемами проходит на самом верхнем уровне классификации (`regulation` / `booking` / `other`) и физически не разделена на отдельные приложения — рассмотрено и осознанно отклонено (см. ADR-лог) из-за высокой цены разделения состояния при малой практической пользе на текущем масштабе.

#### Ключевые решения

- `city` — PostgreSQL ENUM (`Москва`/`Санкт-Петербург`/`Уфа`), не отдельная таблица — осознанное упрощение для трёх фиксированных значений.
- `users.name` — без нормализации и без уникальности; поиск строго по точному совпадению строки. Отражает отсутствие полноценной авторизации в системе (нет `user_id` из внешней identity-системы).
- **Партиционированный уникальный индекс** `unique_active_booking (car_id, booking_date) WHERE status = 'confirmed'` — гарантия на уровне БД против двух активных броней на одну машину/дату.
- **Триггер + advisory lock** — бизнес-правило "один сотрудник — максимум одна активная бронь в городе на дату" реализовано в двух местах: BEFORE-триггер на `bookings` (ловит любой путь записи) и `pg_advisory_xact_lock` внутри `reserve_available_car` (защита от гонки параллельных запросов, которую триггер сам по себе не закрывает).
- `created_at`/`updated_at` — сознательно исключены из `cars`/`users`/`bookings` на этапе MVP; появились только в `audit_log`, где именно для этого таблица и существует.

#### RLS

Row Level Security включён на всех таблицах. Явные deny-политики (`USING (false)`) для ролей `anon`/`authenticated`. Весь легитимный доступ идёт через `service_role` (используется Dify-интеграцией) — RLS его не затрагивает по определению; RPC-функции с `SECURITY DEFINER` также обходят RLS. Защита нацелена на гипотетический сценарий утечки/использования `anon`-ключа, не на текущий рабочий путь.

### 3. RPC-слой

Вся бизнес-логика, требующая JOIN, транзакционности или атомарности, вынесена в PostgreSQL-функции (`SECURITY DEFINER`, с явным `search_path`), вызываемые из Dify через HTTP-узлы (`POST /rest/v1/rpc/<function>`), а не через штатный CRUD-плагин Supabase — плагин не поддерживает вызов произвольных функций и, как обнаружено при интеграции audit_log, работает не через `service_role`, а под ролью, подпадающей под RLS.

| Функция | Назначение |
|---------|------------|
| `get_available_models` | Список моделей, свободных в городе на дату |
| `get_one_available_car` | Одна свободная машина модели (не атомарна, в pipeline не используется) |
| `reserve_available_car` | Атомарный поиск + бронирование (advisory lock + `FOR UPDATE SKIP LOCKED`) |
| `get_user_active_bookings` | Активные брони сотрудника (текущие и будущие) |
| `find_booking_to_cancel` | Поиск брони для отмены по частичным параметрам |
| `cancel_booking` | Отмена конкретной брони по id |
| `expire_past_bookings` | Служебная — переводит просроченные брони в cancelled, запускается по расписанию через `pg_cron` |
| `log_read_event` | Запись read-события в audit_log |

Полные сигнатуры и edge-cases — см. отдельный документ API Contract.

#### Guard Rail (подтверждение перед мутацией)

Реализован через текстовое подтверждение (не встроенный Dify-узел Human Input — рассмотрен и отклонён из-за платформенного бага с публикацией графа). Состояния хранятся в `conv_confirm_state` (`reserve_confirm`/`cancel_confirm`/`reserve_choice`/`cancel_choice`), текст подтверждения — в `conv_confirm_summary` (переживает повторные показы при неоднозначном ответе пользователя). Ответы пользователя разбираются детерминированным Code-блоком (точное совпадение "да"/"нет"/"прервать"/"заменить"), не LLM — обеспечивает предсказуемость на критичном пути перед мутацией данных.

### 5. Управление состоянием диалога

Ключевое архитектурное решение всего проекта — LLM-память в узлах Dify оказалась недостаточно надёжной для многошаговых сценариев (короткие ответы пользователя неверно классифицировались без явного контекста). Решение — явный слой состояния через **Conversation Variables**, не через встроенную память LLM (память в итоге отключена везде, где раньше применялась для контекста).

#### Основные переменные

| Переменная | Назначение |
|------------|------------|
| `conv_reserve_city/date/model` | Параметры текущего reserve-сценария |
| `conv_cancel_city/date/model` | Параметры текущего cancel-сценария (разделены с reserve — ADR-016, защита от использования чужих данных при ошибке маршрутизации) |
| `conv_employee_name` | ФИО — общее для всех сценариев, не сбрасывается между ними (за исключением явного сброса) |
| `conv_pending_booking_id` | id найденной для отмены брони, сохраняется между шагом поиска и подтверждением |
| `conv_last_intent` | Последнее распознанное намерение — мягкий fallback при неоднозначной классификации |
| `conv_awaiting_clarification` | Жёсткий приоритет — активное состояние ожидания уточнения побеждает даже явный вывод классификатора |
| `conv_confirm_state` / `conv_confirm_summary` | Состояние и текст Guard Rail-подтверждения |

#### Механизм merge (накопление параметров по ходу диалога)

Каждый экстрактор параметров сопровождается Code-блоком, который берёт новое значение, если оно непусто, иначе сохраняет предыдущее из Conversation Variable. Это заменяет LLM-память как способ "помнить" контекст многошагового диалога — состояние детерминированно, не зависит от интерпретации истории моделью.

#### Иерархия приоритетов классификации намерений

1. `conv_awaiting_clarification` (активное ожидание конкретного ответа) — высший приоритет
2. Явный вывод LLM-классификатора
3. `conv_last_intent` (мягкий fallback при неопределённом выводе)
4. Дефолтное значение

#### Единая точка очистки

Все точки завершения сценария (успех, прерывание, команда сброса) используют один общий блок очистки полного набора conv-переменных (кроме `conv_employee_name`) — вместо точечных наборов в каждом месте, что ранее приводило к рассинхронизации при добавлении новых переменных.

### 6. Надёжность и обработка ошибок

- **Fail Branch** на всех HTTP-узлах, вызывающих Supabase RPC — инфраструктурный сбой (таймаут, недоступность) не роняет workflow, а ведёт к понятному сообщению пользователю. Default Value намеренно не используется — не должен маскировать сбой инфраструктуры под пустой бизнес-результат.
- **Валидация вывода LLM кодом** — на каждом уровне классификации (regulation/booking/other, reserve/my_bookings/cancel) вывод модели проверяется по allowed-list с защитным fallback, а не используется напрямую.
- **Explicit-проверка пустого результата RAG** — порог релевантности включён в узле поиска знаний, пустой результат обрабатывается отдельной веткой без вызова LLM (исключает домысливание ответа).

### 7. Наблюдаемость

Единая таблица `audit_log`, комбинированный подход:

- **Мутации** (`bookings`) — через BEFORE/AFTER-триггер на уровне БД, гарантированное покрытие независимо от пути записи.
- **Обращения на чтение** — через явный вызов `log_read_event` из pipeline после каждого read-RPC (успех и сбой), поскольку Postgres не поддерживает триггеры на SELECT.

`actor` — захардкоженное системное значение (`HR_test`), отражающее отсутствие полноценной авторизации; не является криптографически подтверждённой идентификацией.

### 8. Осознанно не реализовано

- Полноценная авторизация / привязка `user_id` к диалогу
- Идемпотентность на случай повторной отправки подтверждения
- RLS-политики с содержательной фильтрацией (`authenticated`-доступ с фильтром по владельцу) — текущие политики только deny-all
- Автоматизация фоновых процессов сверх `expire_past_bookings` (например, уведомления)

Подробности и обоснование каждого решения — в ADR-логе проекта.
