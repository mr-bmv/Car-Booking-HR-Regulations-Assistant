# Product Vision & Capabilities — Car Booking & HR Regulations Assistant

**Version:** 1.0  
**Status:** MVP (Proof of Concept)  
**Last Updated:** 2026-08-14

---

## 1. Product Vision

**Для кого:** Для сотрудников компании, которым нужно быстро узнавать правила командировок/отпусков и бронировать служебные автомобили без обращения в отдел логистики или HR.

**Что делаем:** Единый чат-бот на базе Dify, совмещающий два сценария в одном диалоговом интерфейсе:

1. **Вопросы по регламентам** – ответы строятся на реальных документах компании (RAG) с защитой от галлюцинаций.
2. **Бронирование автомобилей** – поиск свободных машин по городу и дате, создание/отмена брони, просмотр текущих броней – всё в свободном диалоге, без форм и меню.

**Ключевая ценность:** Снижение нагрузки на HR и автопарк, ускорение рутинных операций, единая точка входа для двух разных бизнес-функций.

**Технический стек:** Dify (Chatflow) + Supabase (PostgreSQL) с бизнес-логикой на уровне БД (RPC-функции) и строгим разделением мутаций и чтений.

## 2. Capability Map (Матрица возможностей)

| Уровень | Возможность | Описание |
|---------|-------------|----------|
| **Core** | RAG по регламентам | Поиск по загруженным документам (отпуска, командировки). Честный отказ, если данных нет. |
| **Core** | Просмотр свободных авто | По городу и дате – список доступных моделей. |
| **Core** | Создание брони | Выбор авто из списка → подтверждение → запись в БД с защитой от двойного бронирования. |
| **Core** | Отмена брони | Поиск по номеру брони или автомобилю → подтверждение → удаление. |
| **Core** | Просмотр моих броней | Список активных бронирований текущего сотрудника. |
| **Business** | Диалоговое состояние | Явные переменные (не только память LLM) для предотвращения зацикливаний и неверной классификации. |
| **Business** | Подтверждение действий | Запрос подтверждения перед необратимыми операциями (бронь/отмена). |
| **Business** | Журнал аудита | Логирование всех мутаций (триггеры БД) и чтений (явный вызов из pipeline). |
| **Enterprise** | Row Level Security (RLS) | Дополнительный уровень защиты данных на уровне БД (принцип "защита в глубину"). |
| **Enterprise** | Транзакционная целостность | Блокировки на уровне БД для исключения гонок при параллельных запросах. |

## 3. MVP Scope (Что входит в первую версию)

- [x] Чат-интерфейс в Dify с двумя маршрутами (RAG и бронирование).
- [x] Интеграция с Supabase через RPC-функции.
- [x] Поиск свободных авто по городу и дате.
- [x] Создание брони с проверкой занятости.
- [x] Отмена брони по идентификатору.
- [x] Просмотр списка броней сотрудника.
- [x] RAG-ответы на вопросы по отпускам/командировкам с отказом при отсутствии данных.
- [x] Логирование мутаций (триггеры БД).
- [x] Подтверждение перед бронированием и отменой.

## 4. Out of Scope (Чего НЕ будет в MVP)

- Интеграция с реальным календарём (Outlook/Google) – только ручной ввод дат.
- Оплата или лимиты по бронированию – только доступность авто.
- Многопользовательские роли (админ, менеджер) – только сотрудник и его собственные брони.
- История изменений регламентов – загружается только актуальная версия документов.
- Мобильное приложение – только веб-интерфейс.

## 5. Architectural Principles (Принципы развития)

1. **Данные и бизнес-правила – в БД, а не в промптах.**  
   Вся логика проверки занятости, транзакционности и защиты от гонок реализована на уровне PostgreSQL (RPC, блокировки), а не в LLM.

2. **Явное состояние – надёжнее, чем память модели.**  
   Диалоговое состояние строится на переменных Dify, а не только на контекстном окне – это предотвращает зацикливания и неверную классификацию намерений.

3. **Подтверждение перед любым изменением.**  
   Любая мутация (бронь/отмена) проходит через шаг подтверждения, чтобы избежать случайных действий со стороны пользователя или модели.

4. **Аудит – неотъемлемая часть системы.**  
   Все изменения логируются через триггеры БД; чтения – через явный вызов логирования в пайплайне (поскольку СУБД не перехватывает SELECT'ы).

5. **Защита в глубину.**  
   Даже при доверенном канале доступа (Dify → БД) включена RLS как дополнительный барьер.

6. **Честность LLM.**  
   При RAG – если документ не содержит точного ответа, бот обязан сказать «не нашёл информации», а не придумывать.

## 6. Known Limitations & Future Roadmap

### Текущие ограничения
- **Только один город за раз** – для поиска авто нужно явно указать город.
- **Нет уведомлений** – пользователь не получает push/email о подтверждении или напоминании.
- **RAG работает только по загруженным документам** – нет автоматической синхронизации с корпоративным порталом.
- **Нет обработки естественного языка для дат** – даты должны быть в явном формате (или парсятся через LLM, но без календарной логики).

### Планируемые улучшения
- Расширение RAG на большее количество типов документов (политики безопасности, IT-регламенты).
- Интеграция с календарем для автоматической подстановки занятости авто.
- Дашборд для администратора автопарка.
- Умный парсинг дат и времени через NLP-модуль.
- Возможность бронирования на несколько дней.
