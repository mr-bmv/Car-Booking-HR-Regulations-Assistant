# Architecture Decision Records — Car Booking Chatbot (Dify + Supabase)

## ADR-001: Отказ от Python в пользу JavaScript во всех Code-блоках

**Статус:** Принято

**Контекст:** Разработчик не владеет Python и не планирует его осваивать в рамках проекта; вся логика (нормализация дат, сборка фильтров, парсинг JSON) не требует специфичных Python-библиотек.

**Решение:** Все Code-блоки в Dify пишутся на JavaScript. Python не используется, несмотря на то, что технически доступен в песочнице Dify.

**Последствия:** Единообразие кодовой базы, ниже когнитивная нагрузка при поддержке. Ограничение — недоступны Python-специфичные библиотеки (numpy/pandas), но для задач проекта они не требуются.

## ADR-002: Получение данных из Supabase Get Rows через переменную `json`, а не `text`

**Статус:** Принято

**Контекст:** Плагин `langgenius/supabase` в Dify Chatflow не показывал переменную `json` в автокомплите узла Ответ до первого реального запуска блока (динамическая типизация вывода tool-узлов). Переменная `text` у этого action всегда пустая при структурированном результате.

**Решение:** Использовать `json` как источник данных, добавить промежуточный Code-блок для распаковки вложенной структуры (`json[0].data[...]`) в плоский массив/строку перед передачей в LLM.

**Последствия:** Расхождение в поведении между Dify Workflow и Chatflow задокументировано как особенность платформы, не баг конфигурации.

## ADR-003: Reasoning-модель заменена на обычную для задач классификации

**Статус:** Принято

**Контекст:** `deepseek-v4-flash` (reasoning-модель) возвращала цепочку `<think>...</think>` внутри поля `text`, ломая точное сравнение в узлах ЕСЛИ/ИНАЧЕ. `reasoning_content` оставался пустым — провайдер не разделял потоки.

**Решение:** Для классификаторов интентов (блоки intent-классификации) используется обычная нерассуждающая модель (`deepseek-chat`). Reasoning-модели рассматриваются только для сложных генеративных задач, не для классификации в одно слово.

**Последствия:** Ниже стоимость и латентность классификации, устранена нестабильность формата вывода.

## ADR-004: Фильтры Supabase-плагина без явного оператора `eq`

**Статус:** Принято (эмпирическое наблюдение)

**Контекст:** Плагин `langgenius/supabase` возвращал ошибку при фильтре вида `column=eq.value` — по всей видимости, добавляет `eq` самостоятельно.

**Решение:** Формат фильтра в коде сборки — `column=value`, без явного оператора. Комбинация условий — через запятую (`car_number=X,booking_date=Y`), протестировано и подтверждено рабочим.

**Последствия:** Отклонение от стандартного синтаксиса PostgREST задокументировано, чтобы не воспроизводить ошибку при добавлении новых фильтров.

## ADR-005: Дублирование логики нормализации дат вместо выноса в переиспользуемый Workflow-инструмент

**Статус:** Принято, помечено как временный технический долг

**Контекст:** Одинаковый код нормализации дат используется в нескольких ветках (reserve, cancel). Dify поддерживает публикацию workflow как переиспользуемого инструмента.

**Решение:** На данном этапе — сознательное дублирование кода в разных Code-блоках. Вынос в отдельный переиспользуемый workflow отложен на этап "оптимизация pipeline" (по общему плану проекта: MVP → сложная схема БД → выделение в отдельный слой).

**Последствия:** Риск рассинхронизации логики при будущих правках признан и принят осознанно, а не по недосмотру. Плюс демонстрации взвешенного подхода к DRY (не переусложнять раньше времени).

## ADR-006: Redesign базы данных — нормализованная схема из трёх таблиц

**Статус:** Принято

**Контекст:** Исходная плоская таблица `bookings` (car_number, employee_name, booking_date, is_occupied) не масштабировалась на сценарии с городами и множественными машинами одной модели.

**Решение:** Схема из трёх таблиц — `cars` (id, number, model, city), `users` (id, name), `bookings` (id, car_id, user_id, booking_date, status). Город — тип PostgreSQL ENUM, не отдельная таблица (осознанное упрощение для MVP). Поля `created_at`, `email` исключены как избыточные для текущего функционала.

**Последствия:** Требует JOIN-логики для проверки доступности (город берётся из `cars`, статус — из `bookings`). Поиск пользователя — строго точное совпадение строки `name`, без нормализации и без fuzzy-match (осознанное упрощение; в реальном проекте заменяется на `user_id` из системы авторизации).

## ADR-007: Частичный уникальный индекс против двойного бронирования

**Статус:** Принято

**Контекст:** Проверка доступности и создание брони — два последовательных шага в pipeline, между ними возможна гонка (race condition) при параллельных запросах.

**Решение:** `CREATE UNIQUE INDEX unique_active_booking ON bookings (car_id, booking_date) WHERE status = 'confirmed';` — гарантия на уровне БД, что не может существовать двух активных броней на одну машину/дату, независимо от логики приложения.

**Последствия:** Защита работает даже при ошибках в pipeline-логике. Требует обработки возможной ошибки конфликта на уровне приложения (учтено далее в ADR-009).

## ADR-008: RPC-вызовы через HTTP Request node вместо штатного Supabase-плагина

**Статус:** Принято

**Контекст:** Плагин `langgenius/supabase` в Dify поддерживает только Create/Read/Update/Delete Row(s), не поддерживает вызов произвольных Postgres-функций (RPC).

**Решение:** RPC-функции вызываются через встроенный в Dify узел HTTP-запрос (POST на `/rest/v1/rpc/<function_name>`), с URL и ключом, вынесенными в Environment Variables. Учётные данные Supabase помечены как Secret.

**Последствия:** Дополнительный уровень настройки (заголовки, тело запроса вручную) по сравнению с готовым плагином, но открывает доступ к серверной бизнес-логике (JOIN, транзакции, атомарные операции), недоступной через простой CRUD-плагин.

## ADR-009: Атомарное бронирование через `FOR UPDATE SKIP LOCKED` вместо двухшаговой проверки+вставки

**Статус:** Принято

**Контекст:** Изначальный план (RPC "найти свободную машину" → отдельный HTTP-вызов INSERT) оставлял зазор гонки между чтением и записью, аналогичный проблеме из ADR-007, но на уровне выбора конкретной машины среди нескольких экземпляров модели.

**Решение:** Единая PL/pgSQL-функция `reserve_available_car`, выполняющая выбор свободной машины (`FOR UPDATE SKIP LOCKED`) и `INSERT` в одной транзакции. Функция `get_one_available_car` (два отдельных шага) сохранена в БД, но не используется в продуктивном pipeline.

**Последствия:** Гонка устранена на уровне транзакционной семантики БД, а не постфактум через перехват ошибки уникальности. Функция `reserve_available_car` не переиспользует более раннюю `get_one_available_car` — сознательное решение в пользу атомарности вместо переиспользования кода.

## ADR-010: Фильтр "активных броней пользователя" — по будущим датам, а не по календарному месяцу

**Статус:** Принято (пересмотр после первоначальной реализации)

**Контекст:** Первая версия `get_user_active_bookings` фильтровала по `date_trunc('month', booking_date) = date_trunc('month', CURRENT_DATE)`. Не соответствовало бизнес-логике: сотруднику важны все будущие брони, а не только брони в границах календарного месяца.

**Решение:** Условие изменено на `booking_date >= CURRENT_DATE`. Добавлена отдельная функция `expire_past_bookings()` для перевода просроченных `confirmed`-записей в `cancelled` (запускается вручную или потенциально через `pg_cron`), как дополнительная гигиена данных, не заменяющая фильтр в основном запросе.

**Последствия:** Корректный ответ пользователю не зависит от того, когда в последний раз выполнялась фоновая очистка.

## ADR-011: Объединение намерений "check" и "reserve" в единый intent

**Статус:** Принято (пересмотр после редизайна БД)

**Контекст:** После редизайна БД старая ветка "check" (проверка по `car_number` в плоской таблице) перестала соответствовать структуре данных — не выполняла необходимый JOIN с `cars`. Возник вопрос, чинить ли старую ветку отдельно или объединять с "reserve".

**Решение:** "check" и "reserve" объединены в единое намерение `reserve` — оба сценария используют один и тот же путь (RPC `get_available_models` → выбор модели → RPC `reserve_available_car`), различие "просто посмотреть" vs "забронировать" естественно разрешается ходом диалога, без отдельной ветки в классификаторе.

**Последствия:** Классификатор `<13>` упрощён до трёх значений (`reserve`, `my_bookings`, `cancel`) вместо четырёх. Старая ветка check (блоки построения фильтра по `car_number`) удалена из графа.

## ADR-012: Conversation Variables вместо LLM-памяти для отслеживания состояния диалога

**Статус:** Принято (после серии итераций)

**Контекст:** Изначальная попытка полагаться на встроенную память LLM-экстракторов для многошаговых сценариев (например, "покажи доступные машины" → "10 августа" → "для Иванова") приводила к нестабильному поведению: короткие ответы без явного контекста классифицировались неверно (`other` вместо `booking`), включение памяти в классификаторе намерений (`<2>`) вызывало зацикливание диалога.

**Решение:** Введены явные Conversation Variables (`conv_city`, `conv_date`, `conv_model`, `conv_employee_name`, `conv_last_intent`) с детерминированной merge-логикой в Code-блоках (новое значение побеждает, если оно непустое, иначе сохраняется старое). Код-валидатор после классификатора намерений (`<2.5>`) принудительно переопределяет неоднозначный/ошибочный вывод LLM на `booking`, если в контексте диалога уже есть незавершённые booking-данные. Аналогичный fallback введён на уровне под-классификатора (`<13.5>`) через `conv_last_intent`.

**Последствия:** Детерминированное отслеживание состояния независимо от того, "вспомнит" ли LLM контекст. Память LLM в классификаторах (`<2>`, `<13>`) отключена; используется только в экстракторах параметров (позднее заменена на явный merge через Conversation Variables). Требует явного сброса переменных состояния в точках завершения сценария (успешная бронь/отмена, таймаут, прерывание) во избежание утечки контекста в несвязанные последующие запросы.

## ADR-013: Guard Rail-подтверждение перед мутирующими операциями — отложено

**Статус:** ~~Отклонено на текущем этапе, зафиксировано в бэклоге~~ **Superseded by ADR-025**

**Контекст:** Спроектирован и частично реализован механизм подтверждения перед bronированием/отменой через встроенный узел Dify "Human Input" (кнопки Да/Нет, Прервать/Заменить, таймаут). При попытке публикации приложения возникла ошибка платформы — граф не распознавал существующие и рабочие связи между Human Input узлами (подтверждено воспроизводимым багом, зафиксированным также в публичных issues платформы).

**Решение:** Реализация на основе Human Input node отменена. Логика подтверждения возвращена к версии без Guard Rail. Спроектированное решение (включая схему ветвления, тексты подтверждения, логику "Прервать"/"Заменить" с сохранением merge-логики Conversation Variables) сохранено как экспортированный DSL в незадеплоенной ветке для демонстрации проектной работы.

**Последствия:** Функциональность подтверждения действий отсутствует в продуктивной версии. Альтернативная реализация через текстовое подтверждение (без Human Input node) рассматривается как возможный следующий шаг, приоритет не определён.

## ADR-014: RLS в Supabase не реализован в рамках MVP

**Статус:** ~~Отложено, зафиксировано в бэклоге~~ → **Superseded by ADR-021**

**Контекст:** Доступ к таблицам Supabase осуществляется исключительно через `service_role` ключ, используемый Dify-интеграцией. Row Level Security не включён.

**Решение:** Для MVP защита ограничивается секретностью `service_role` ключа (хранится как Environment Variable/Secret в Dify). Явные политики RLS не настраивались.

**Последствия:** Признанный пробел в защите на уровне БД — задокументирован как известное ограничение и кандидат на реализацию в числе первых пунктов доработки после MVP.

## ADR-016: Разделение Conversation Variables по веткам reserve/cancel

**Статус:** Принято

**Контекст:** Единые переменные `conv_city`/`conv_date`/`conv_model` использовались одновременно веткой reserve и веткой cancel. При ошибочной маршрутизации между ветками (см. ADR-018) это приводило не просто к неверному ответу, а к реальному побочному действию в БД — данные, введённые для отмены брони, использовались как параметры нового бронирования.

**Решение:** Переменные разделены на `conv_reserve_city/date/model` и `conv_cancel_city/date/model`. `conv_employee_name` оставлен общим — ФИО не специфично для сценария. Деление сделано только между reserve и cancel: my_bookings использует исключительно `conv_employee_name` и не участвует в конфликте.

**Последствия:** Ошибочная маршрутизация в чужую ветку теперь приводит к безопасному запросу недостающих параметров, а не к выполнению операции с чужими данными.

## ADR-017: Бизнес-правило "одна активная бронь на сотрудника в городе на дату"

**Статус:** Принято

**Контекст:** При тестировании обнаружен сценарий, где у одного сотрудника оказывалось несколько активных броней в одном городе на одну дату (разные машины одной модели), что делало отмену по описанию (модель+город+дата) неоднозначной. Рассматривался вариант добавления номера машины как дополнительного различающего параметра.

**Решение:** Вместо добавления номера машины как способа различения — введено бизнес-ограничение: один сотрудник не может иметь более одной активной брони в одном городе на одну дату. Реализовано на двух уровнях: (1) BEFORE-триггер на таблице `bookings`, проверяющий отсутствие конфликта через JOIN с `cars`; (2) `pg_advisory_xact_lock` внутри `reserve_available_car` по ключу (user_id, city, date) для защиты от гонки при параллельных запросах — обычной проверки `EXISTS` недостаточно, т.к. два параллельных запроса могут пройти её одновременно до коммита.

**Последствия:** Неоднозначность при отмене брони устранена на уровне данных, а не патчем в логике поиска. Правило защищено независимо от пути записи (в том числе от прямой вставки в обход RPC-слоя).

## ADR-018: Явная команда сброса состояния ("Новый запрос" / "Отмена")

**Статус:** Принято

**Контекст:** При тестировании обнаружены случаи, когда пользователь не мог выйти из состояния ожидания уточняющего ответа (например, из уточнения города/даты) — короткие ответы пользователя неверно классифицировались, диалог зацикливался.

**Решение:** Введена детерминированная проверка точной команды сброса (`"новый запрос"`, `"отмена"`, с учётом регистра/пунктуации) через Code-блок, выполняемая ДО LLM-классификатора намерений, а не через LLM. При срабатывании — очистка всех Conversation Variables и переход к приветственному ответу. Все промежуточные уточняющие ответы во всех ветках дополнены единой текстовой подсказкой о существовании этой команды.

**Последствия:** Гарантированный выход из любого состояния диалога, не зависящий от качества классификации LLM. Осознанно не реализовано через LLM — точное совпадение строки не требует вероятностной интерпретации.

## ADR-019: Приоритет "ожидания уточнения" над явным выводом классификатора намерений

**Статус:** Принято

**Контекст:** Ранее принятое правило (ADR-012: контекст побеждает "other", но не побеждает явный вывод классификатора) оказалось недостаточным — сообщение пользователя, отвечающее на уточняющий вопрос ветки cancel, но содержащее booking-специфичные детали (модель, город, дата), классифицировалось как явный `reserve`, уводя диалог в чужую ветку с последующим нежелательным действием.

**Решение:** Введена Conversation Variable `conv_awaiting_clarification`, устанавливаемая непосредственно перед уточняющим вопросом конкретной ветки (например, при нескольких найденных бронях в cancel) и сбрасываемая после получения ответа. В коде-валидаторе под-классификатора приоритет пересмотрен: активное состояние ожидания уточнения побеждает даже явный вывод LLM-классификатора, который теперь уступает только этому состоянию, но по-прежнему побеждает мягкий контекст (`conv_last_intent`).

**Последствия:** Иерархия приоритетов классификации усложнена до трёх уровней (явное ожидание уточнения → явный вывод классификатора → мягкий контекст → дефолт). Требует дисциплины: любая новая точка ветвления с уточняющим вопросом должна выставлять и сбрасывать эту переменную по аналогичной схеме.

## ADR-020: Встроенный узел Dify "Question Classifier" рассмотрен и отклонён

**Статус:** Отклонено

**Контекст:** Dify предоставляет специализированный узел Question Classifier с нативным ветвлением по классам сразу после LLM-классификации, историей диалога как встроенной опцией и полем Instructions для уточняющих правил.

**Решение:** Не использовать для замены текущей связки LLM+Code-валидатор. Причина: нативное ветвление в Question Classifier происходит непосредственно после ответа модели, не оставляя точки для вставки кастомной логики переопределения (allowed-list валидация, приоритет `conv_awaiting_clarification`, fallback на `conv_last_intent` — см. ADR-012, ADR-019). Использование узла потребовало бы всё равно добавлять Code-блок постфактум, нивелируя выигрыш от нативного ветвления.

**Последствия:** Классификация намерений продолжает строиться на связке LLM-узел + Code-блок валидации + ЕСЛИ/ИНАЧЕ, а не на специализированном узле платформы. Решение задокументировано как осознанно рассмотренная и отклонённая альтернатива.

## ADR-021: Row Level Security включён на всех таблицах

**Статус:** Принято

**Контекст:** Изначально (ADR-014) доступ к таблицам ограничивался исключительно секретностью `service_role` ключа, используемого Dify-интеграцией. RLS не был включён — таблицы были технически открыты для полного доступа через REST API для любого, кто узнал бы `anon` или `service_role` ключ.

**Решение:** RLS включён на всех трёх таблицах (`cars`, `users`, `bookings`). Явные deny-политики созданы для ролей `anon` и `authenticated` (`USING (false)`, `FOR ALL`) — документируют намерение явно, хотя technically избыточны при отсутствии политик (RLS default-deny и так закрывает доступ). `service_role`, используемый ботом, RLS игнорирует по определению — функциональность приложения не затронута.

**Последствия:** Прямой доступ к таблицам через публичный `anon` ключ (даже при случайной утечке) не даёт доступа к данным. RPC-функции с `SECURITY DEFINER` (см. ADR-008/009) продолжают обходить RLS так же, как обходит его `service_role` — это осознанная особенность `SECURITY DEFINER`, не пробел в защите, поскольку сами функции вызываются исключительно через доверенный HTTP-слой с `service_role` ключом.

## ADR-022: Fail Branch для HTTP-узлов вместо аварийного завершения workflow

**Статус:** Принято

**Контекст:** Все HTTP-узлы, вызывающие Supabase RPC, были настроены с обработкой ошибок по умолчанию (None) — сбой инфраструктуры (таймаут, недоступность сервиса) приводил к полному аварийному завершению workflow без какого-либо ответа пользователю в чате.

**Решение:** На всех 5 HTTP-узлах включён режим Fail Branch. Каждый узел получил локальный (расположенный рядом на графе) блок Ответа для случая сбоя, чтобы избежать протянутых через весь холст связей к единому узлу. Тексты ошибок и другие часто переиспользуемые статичные фразы (включая подсказку про команду сброса) вынесены в Environment Variables (`INFRA_ERROR_MESSAGE`, `RESET_HINT_TEXT`) — единая точка изменения текста при сохранении локальности графа. Default Value не использовался — намеренно, чтобы не маскировать инфраструктурный сбой под бизнес-результат (например, пустой список машин).

**Последствия:** Пользователь получает осмысленный ответ при любом сбое интеграции с Supabase, а не тишину. Различие между "система ответила: данных нет" и "система не ответила" сохранено явно.

## ADR-023: Audit log — комбинированный подход (триггер + явное логирование)

**Статус:** Принято

**Контекст:** Требовалось отслеживать не только мутации данных (кто/что/когда изменил), но и обращения на чтение (кто какие данные запрашивал) — реалистичный сценарий расследования (запросил доступность → получил список → отменил чужую бронь → забронировал на сообщника). Postgres не поддерживает триггеры на SELECT — это фундаментальное ограничение движка, не архитектурное решение.

**Решение:** Единая таблица `audit_log` с полем `event_type` (`read`/`mutation`) для целостной хронологии. Мутации (`bookings`) логируются через триггер `AFTER INSERT OR UPDATE` — гарантированное покрытие независимо от пути записи. Чтение логируется явно из pipeline через отдельную RPC-функцию `log_read_event` (`SECURITY DEFINER`), вызываемую после каждого из трёх read-RPC (get_available_models, get_user_active_bookings, find_booking_to_cancel) — как на успешном пути (с `result_count`), так и на fail-ветке (с текстом ошибки).

Первая попытка реализовать запись через штатный плагин Supabase (Create Row) провалилась — плагин работает не через `service_role`, а под ролью, подпадающей под RLS, и был заблокирован deny-политикой (ADR-021). Решение — перейти на RPC с `SECURITY DEFINER`, единообразно с остальной архитектурой проекта (см. ADR-008). После обнаружения этого расхождения проведена проверка всего графа Dify на предмет оставшихся узлов плагина `langgenius/supabase` (Get Rows/Create Row/Update Row) — таких узлов в pipeline не найдено, весь функционал уже был переведён на HTTP+RPC ранее (ADR-008), риск скрытой поломки других веток из-за RLS не подтвердился.

**Ограничения:** `actor` — захардкоженное значение `'HR_test'` (не полноценная идентификация, авторизации в системе нет — см. ADR-006). Неизменяемость лога для `service_role` обеспечивается только дисциплиной кода (RPC не содержит UPDATE/DELETE на audit_log), не техническим ограничением — RLS не может ограничить `service_role`. Сбой записи лога (Default Value на HTTP-узлах) не прерывает основной пользовательский сценарий — логирование вторично по отношению к функциональности бота.

**Последствия:** Полный журнал доступа и изменений доступен для последующего анализа (в т.ч. сценариев расследования злоупотреблений). Дальнейшее использование только RPC+HTTP для любых новых интеграций с БД закреплено как фактическая практика проекта, а не только как рекомендация.

## ADR-024: Единый блок очистки Conversation Variables в точках завершения сценария

**Статус:** Принято

**Контекст:** Точечная очистка переменных в каждой точке завершения (после успешной брони, успешной отмены, прерывания) требовала поддерживать отдельный, вручную подобранный список переменных в каждом месте. Это создавало риск рассинхронизации — при добавлении новой Conversation Variable (например, `conv_pending_booking_id` при доработке Guard Rail для cancel) требовалось находить и обновлять все точки очистки вручную, и одна из них была пропущена на практике.

**Решение:** Введён единый блок очистки, вызываемый во всех точках завершения сценария (успешная бронь, успешная отмена, abort из Guard Rail) — чистит полный набор conv-переменных разом: `conv_reserve_city/date/model`, `conv_cancel_city/date/model`, `conv_pending_booking_id`, `conv_confirm_state`, `conv_last_intent`, `conv_awaiting_clarification`. Исключение — `conv_employee_name`, сохраняется между сценариями осознанно (сотрудник может продолжать работать от своего имени без повторного представления).

**Важное уточнение:** это решение действует на другой стадии жизненного цикла диалога, чем разделение `conv_reserve_*`/`conv_cancel_*` (см. ADR-016). ADR-016 защищает от использования чужих данных **во время** диалога, пока сценарий ещё не завершён (например, при ошибочной маршрутизации между ветками); данное решение унифицирует очистку **в момент завершения** сценария, когда все данные в любом случае подлежат сбросу вне зависимости от того, какая ветка отработала. Оба решения не противоречат друг другу и действуют совместно.

**Последствия:** Добавление новой Conversation Variable в будущем требует правки только одного блока вместо поиска всех точек очистки по графу. Риск "зависшего" состояния между сценариями снижен.

## ADR-025: Guard Rail реализован через текстовое подтверждение

**Статус:** Принято

**Контекст:** После отказа от Human Input node (ADR-013) функциональность подтверждения перед мутацией осталась нереализованной. Решено вернуться к задаче, используя уже отработанный в проекте паттерн Conversation Variables вместо нативных UI-кнопок.

**Решение:** Подтверждение реализовано как последовательность текстовых состояний (`conv_confirm_state`: reserve_confirm/cancel_confirm/reserve_choice/cancel_choice), с детерминированным (не LLM) разбором ответов "да"/"нет"/"прервать"/"заменить". Полный текст подтверждения сохраняется в `conv_confirm_summary` (Conversation Variable, не локальный output блока) — необходимо для корректного повторного показа при неоднозначном ответе пользователя, так как локальная переменная блока недоступна при повторном заходе с другого узла графа. `conv_awaiting_clarification` расширен: устанавливается не только при неоднозначном поиске (cancel_disambiguation), но и в состоянии "жду замену параметра" (reserve_clarification/cancel_disambiguation), иначе явный вывод классификатора намерений может увести диалог в другую ветку на середине уточнения (обнаружено тестированием — ответ с booking-специфичными словами после "Заменить" ошибочно классифицировался как новый запрос reserve вместо продолжения cancel).

**Последствия:** Ветка `unclear` при повторном показе учитывает тип ожидаемого ответа (confirm vs choice) — показывает соответствующий вопрос, а не произвольный текст. Единый блок очистки (ADR-024) применяется и здесь. Менее устойчиво к формулировкам, чем нативные кнопки (только точное совпадение "да"/"нет"/"прервать"/"заменить"), что зафиксировано в Known Limitations как осознанный компромисс.

## ADR-026: Отключение LLM-памяти в экстракторах параметров

**Статус:** Принято

**Контекст:** С введением Conversation Variables и merge-логики (ADR-012, ADR-016) вся смысловая непрерывность многошаговых сценариев уже обеспечивалась явным состоянием, а не памятью LLM. Встроенная память экстракторов (`<48>`, `<34>`, `<28>`) дублировала эту функцию, добавляя недетерминированность без функциональной необходимости.

**Решение:** Память отключена во всех трёх экстракторах параметров. Каждый вызов извлекает данные только из текущего сообщения; накопление контекста полностью на Conversation Variables.

**Последствия:** Упрощена диагностика (каждый вызов экстрактора — чистая функция от одного сообщения), устранён источник недетерминированного поведения. Функциональность многошаговых сценариев не пострадала, подтверждено регрессионным тестированием.

## ADR-027: Переход к Finite State Machine / Session Lock для маршрутизации диалога

**Статус:** Принято

**Контекст:** Маршрутизация намерений строилась на многоуровневой системе приоритетов (`ADR-012`, `ADR-016`, `ADR-019`): явный вывод LLM-классификатора, мягкий контекст `conv_last_intent`, жёсткий приоритет `conv_awaiting_clarification`. Система работала, но патчилась реактивно — каждый новый найденный на практике случай неверной маршрутизации (booking-специфичные слова во время cancel-уточнения, слова "отмени" во время reserve-подтверждения и т.д.) требовал точечного добавления ещё одного условия приоритета. Это создавало растущую сложность без структурной гарантии, что новый похожий случай не появится снова.

**Решение:** Введена явная блокировка активной ветки диалога — `conv_active_branch` (reserve/cancel/my_bookings/пусто) и `conv_branch_step` (collecting/confirming/choosing). Пока `conv_active_branch` не пуст, LLM-классификаторы намерений (`<2>`, `<13>`) не вызываются вообще — сообщение направляется напрямую во внутренний роутер активной ветки, определяющий по `conv_branch_step`, какой обработчик должен получить управление. Классификация происходит только когда `conv_active_branch` пуст, то есть вне активного сценария. Реализовано поэтапно: сначала на ветке my_bookings (простейший случай, без confirmation-подсостояний), затем на reserve, затем на cancel — с промежуточным тестированием на каждом шаге.

Архитектурно это Finite State Machine с session-level context lock: один активный сценарий на сессию, явные условия выхода (успех, явная команда сброса, ошибка).

**Последствия:** Класс багов "неверная маршрутизация LLM-классификатором на середине активного сценария" устранён структурно, а не патчем под конкретный найденный случай — классификатор физически не может вмешаться, пока ветка заблокирована. `conv_awaiting_clarification` и `conv_last_intent` признаны избыточными и удалены — их функцию полностью взяла на себя пара `conv_active_branch`/`conv_branch_step`. `<13.5>` упрощён до чистой allowed-list валидации без слоёв контекстного переопределения. `ADR-019` считать замещённым данным решением.

## ADR-028: Объединение conv_reserve_*/conv_cancel_* в единые переменные — рассмотрено и отклонено

**Статус:** Отклонено

**Контекст:** После введения session lock (ADR-027) возник вопрос: раз неверная маршрутизация между ветками больше невозможна, сохраняет ли смысл разделение `conv_reserve_city/date/model` и `conv_cancel_city/date/model` (введённое в ADR-016 именно для защиты от использования чужих данных при ошибке маршрутизации)? Рассматривалось объединение в общие `conv_city`/`conv_date`/`conv_model` для сокращения дублирования кода (merge-блоков, промптов).

**Решение:** Объединение отклонено. ADR-016 защищал не только от неверной маршрутизации между ветками в моменте — session lock действительно закрывает эту часть проблемы, — но и от утечки данных **между сценариями одного типа, разнесёнными во времени** в рамках одной сессии (например, если единый блок очистки состояния даст сбой или не будет вызван при каком-либо ещё не предусмотренном пути завершения сценария). Проект уже неоднократно сталкивался с рассинхронизацией именно в блоках очистки (пропущенная `conv_pending_booking_id`, не полностью очищенный `conv_reserve_model` при команде сброса) — при объединённых переменных цена каждой такой будущей ошибки очистки возрастает: вместо утечки данных в рамках одной ветки возникала бы утечка данных **между reserve и cancel**, то есть возврат к исходной проблеме ADR-016, но без диагностируемого явного бага маршрутизации — тихая, трудно обнаруживаемая порча данных вместо явно наблюдаемого некорректного поведения.

**Последствия:** Разделение `conv_reserve_*`/`conv_cancel_*` сохранено. Задача сокращения дублирования кода (если станет актуальной) предложено решать иначе — параметризацией самого merge-блока по имени ветки, а не слиянием переменных состояния.

## ADR-029: Command Pattern для мутирующих операций

**Статус:** Принято (задокументировано постфактум — паттерн уже применялся неформально до явной формализации)

**Контекст:** Каждая мутирующая операция (бронирование, отмена) требует сбора нескольких параметров из разных источников (Conversation Variables, экстракторы LLM), их валидации, и выполнения только после явного подтверждения пользователем (Guard Rail, `ADR-025`). Прямой вызов RPC сразу по мере извлечения параметров создавал бы риск выполнения с неполными/невалидными данными и не оставлял бы точки для вставки подтверждения между "решение принято" и "действие выполнено".

**Решение:** Каждая мутация оформлена как отдельный, самодостаточный объект-команда — Code-блок, собирающий все необходимые параметры в единую структуру (JSON-тело запроса) перед вызовом соответствующего RPC. Сборка команды (`<24>`, `<37.5>` и аналогичные блоки) отделена от её выполнения (`<58>`, `<43>`) явным промежуточным шагом — Guard Rail-подтверждением. Между сборкой и выполнением команда хранится в Conversation Variables (`conv_reserve_*`/`conv_cancel_*`, `conv_pending_booking_id`), что равносильно классическому хранению команды как объекта до её исполнения.

**Последствия:** Разделение "что делать" от "когда это выполнить" даёт естественную точку для подтверждения, логирования (`ADR-023`) и последующей идемпотентности (см. `Known Limitations`) — все они технически возможны именно потому, что команда существует как обособленная сущность, а не выполняется немедленно по готовности данных. Единый формат команды (`{action, params}`) между ветками не унифицирован — каждая ветка использует свою структуру, собираемую в отдельном Code-блоке; унификация рассмотрена как возможное архитектурное улучшение, но признана не имеющей функциональной ценности при текущем масштабе (две мутирующие ветки с разными наборами параметров) и не реализована.

## ADR-030: Repository Pattern для доступа к данным

**Статус:** Принято (задокументировано постфактум)

**Контекст:** С самого начала проекта (`ADR-008`) было принято решение отказаться от штатного CRUD-плагина Dify в пользу RPC-функций, вызываемых через HTTP. Это решение фактически реализует Repository Pattern — единую точку доступа к данным, скрывающую детали хранения от вызывающего кода.

**Решение:** Весь доступ к таблицам `cars`, `users`, `bookings`, `audit_log` из pipeline идёт исключительно через именованные RPC-функции (`get_available_models`, `reserve_available_car`, `find_booking_to_cancel`, `cancel_booking`, `get_user_active_bookings`, `log_read_event` и т.д.) — ни один Dify-узел не выполняет прямой `SELECT`/`INSERT`/`UPDATE` к таблице. Полный контракт этого слоя — `api-contract.md`.

**Исключение, зафиксированное явно:** BEFORE/AFTER-триггер на `bookings` (`ADR-023`, логирование мутаций) обращается к таблицам напрямую средствами SQL внутри самой БД, а не через RPC-слой. Это не нарушение принципа — триггер является частью уровня данных, а не частью вызывающего приложенческого кода (pipeline в Dify), и потому находится вне зоны действия этого паттерна по определению, а не в виде отступления от него.

**Последствия:** Любое будущее изменение структуры таблиц (добавление полей, смена типов) требует правки только в RPC-слое — pipeline в Dify не содержит знаний о структуре таблиц напрямую. Новый сценарий, требующий доступа к данным, обязан получить отдельную RPC-функцию, а не обращаться к таблицам в обход неё — это правило зафиксировано как обязательная практика проекта, а не рекомендация.

## ADR-031: Correlation ID (request_id) для трассировки — ограничен read-событиями

**Статус:** Отложено

**Контекст:** Требовалось добавить сквозной идентификатор запроса для трассировки последовательности действий одного пользователя через несколько логируемых событий. Read-события логируются явно из pipeline (`log_read_event`), где доступны Conversation Variables — `request_id` может быть передан как параметр. Mutation-события логируются BEFORE/AFTER-триггером на `bookings` (`ADR-023`) — триггер выполняется на уровне БД и не имеет доступа к состоянию Dify-сессии.

**Решение:** `conv_request_id` генерируется заново в начале каждого диалогового хода и передаётся во все три read-RPC как часть `p_details` в `log_read_event` — попадает в `audit_log` для событий `search_available_models`, `search_own_bookings`, `search_booking_to_cancel` (успех и сбой). Для mutation-событий (`booking_created`, `booking_status_changed`) `request_id` не передаётся и не логируется — рассмотрен вариант дублирующей записи в `audit_log` напрямую из тела RPC-функций (`reserve_available_car`/`cancel_booking`) в дополнение к триггеру, отклонён как избыточное дублирование логирования одного события двумя источниками.

**Последствия:** Полная трассировка "запрос → результат" доступна только для read-событий. Связь read-события с последующей мутацией того же диалогового хода восстанавливается по `actor` и близости по времени (`occurred_at`), не по единому `request_id` — задокументированное ограничение, не пробел, оставленный незамеченным.

## ADR-032: Вынос RAG в отдельное приложение — booking оставлен монолитным

**Статус:** Принято

**Контекст:** После выноса RAG-подсистемы в отдельное дочернее Dify-приложение (вызываемое через HTTP из родительского) рассматривался аналогичный перенос всей booking-логики в собственное дочернее приложение — по образцу микросервисной декомпозиции, где родительское приложение выступает тонким роутером между независимыми "сервисами".

**Решение:** RAG вынесен успешно, потому что он stateless по своей природе — каждый вопрос самодостаточен, разделение потребовало передачи только текста вопроса, без состояния между сообщениями. Booking, напротив, полностью построен на многошаговом диалоговом состоянии (`ADR-027` — session lock, `ADR-025` — Guard Rail с состояниями confirm/choice, `ADR-012`/`ADR-016` — накопление параметров через Conversation Variables между сообщениями). Разделение потребовало бы одного из двух вариантов:

1. Дочернее приложение полностью stateless, родитель передаёт весь снимок состояния (`conv_*`) при каждом вызове и получает обновлённое состояние обратно — реализуемо, но размывает границу ответственности (дочернее приложение содержит логику, но не владеет состоянием; родитель владеет состоянием, но должен знать структуру дочерней логики, чтобы передавать и интерпретировать её).
2. Дочернее приложение владеет собственной сессией на протяжении всего сценария — требует, чтобы механизм Dify (Workflow as Tool) поддерживал длящийся диалог с сохранением состояния между несколькими вызовами в рамках одного пользовательского сценария, что не подтверждено платформенно на момент оценки.

Оценка трудозатрат варианта 1 (реалистичного технически) — 15–25 часов, сопоставимо или больше объёма работы, уже вложенного в session lock и Guard Rail вместе взятые, без гарантии, что платформа вообще спроектирована для передачи такого объёма состояния через границу HTTP-вызова на каждый диалоговый ход.

**Последствия:** Booking-подсистема остаётся частью монолитного родительского приложения. Архитектурная граница между RAG и booking проведена там, где она даётся малой ценой (на stateless-компоненте), а не там, где она была бы архитектурно "красивее", но потребовала бы непропорциональных трудозатрат на перенос сложного состояния через границу процессов. Решение зафиксировано как явно рассмотренное и обоснованно отложенное — не пропущенный шаг, а результат оценки трудозатрат/пользы. Возврат к вопросу целесообразен, если проект дорастёт до конкретной практической причины разделения (например, появление второго независимого потребителя booking-логики, отдельного от текущего чат-интерфейса) — по аналогии с обоснованием отказа от разделения на подсистемы в целом, рассмотренным ранее.
