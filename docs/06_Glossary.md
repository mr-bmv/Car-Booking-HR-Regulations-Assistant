# Глоссарий проекта — что означает каждый термин и где это реализовано

*Этот документ переводит технические термины из вакансий AI/Agent-инженеров на простой язык и показывает, где именно в проекте каждое понятие реализовано на практике — с указанием конкретного файла/раздела для проверки.*

---

## Архитектура

**Что это.** Общий план того, как устроена система: из каких частей она состоит, как эти части связаны, что за что отвечает.

**Где в проекте.** Вся система спроектирована как набор чётко разделённых слоёв: диалоговый интерфейс (Dify) → уровень бизнес-логики (PostgreSQL-функции) → уровень данных (таблицы с ограничениями целостности). Полная схема — `architecture-overview.md`. Каждое значимое архитектурное решение (а их больше 25) задокументировано отдельно с обоснованием — `adr-log.md`.

---

## Интеграции

**Что это.** Соединение системы с внешними сервисами — базами данных, API других программ — так, чтобы они работали вместе.

**Где в проекте.** Интеграция с базой данных Supabase через REST API — не напрямую, а через собственный слой серверных функций (RPC). Есть задокументированный опыт смены подхода к интеграции: изначально использовался готовый плагин, затем — при обнаружении его ограничений (не поддерживает сложную логику, обходит систему безопасности по-другому, чем предполагалось) — переход на прямые HTTP-вызовы к базе данных. См. `ADR-008`, `ADR-023`.

---

## Управление состоянием (State Management)

**Что это.** То, как система «помнит», на каком этапе разговора находится пользователь, и что он уже сказал раньше, чтобы не переспрашивать заново и не терять контекст.

**Где в проекте.** Реализовано через явные переменные состояния диалога (Conversation Variables) — например, система помнит выбранный город, дату, модель машины и имя сотрудника по ходу всего разговора, даже если эти данные назывались в разных сообщениях. Есть отдельное задокументированное решение о том, почему обычная «память» AI-модели для этого не подошла и пришлось делать более надёжный, явный механизм — `ADR-012`. Раздел 5 в `architecture-overview.md`.

---

## State Machine (машина состояний)

**Что это.** Формальная модель поведения системы, где в каждый момент времени система находится в одном из чётко определённых «состояний», и есть точные правила, какие переходы между состояниями разрешены.

**Где в проекте.** Диалог подтверждения перед бронированием/отменой брони — это реализованная state machine с состояниями: «жду подтверждения» → «жду выбора прервать/заменить» → «жду новое значение» → снова «жду подтверждения», плюс явные переходы при командах сброса. Схема переходов описана в `ADR-025`, раздел «Guard Rail» в `architecture-overview.md`.

---

## Маршрутизация запросов (Intent Routing)

**Что это.** Определение того, какую именно задачу хочет решить пользователь по тексту его сообщения, и направление разговора по соответствующему сценарию.

**Где в проекте.** Двухуровневая маршрутизация: сначала общая тема (вопрос про регламенты / бронирование машин / что-то другое), затем — внутри бронирования — конкретное действие (посмотреть доступность, забронировать, посмотреть свои брони, отменить). Раздел 4 в `architecture-overview.md`.

---

## Проектирование Intent Map (карта намерений)

**Что это.** Документ/схема, описывающая: какие намерения пользователя система должна распознавать, какие данные нужны для каждого намерения, что делать, если данных не хватает, куда вести дальше.

**Где в проекте.** Реализовано как явная схема для каждого из 4 намерений (regulation / reserve / my_bookings / cancel):

| Намерение | Обязательные параметры | Fallback при нехватке данных | Переход дальше |
|----|----|----|----|
| **reserve** (бронирование) | город, дата, модель, ФИО | уточняющий вопрос по конкретному недостающему полю | Guard Rail-подтверждение → бронирование |
| **my_bookings** (мои брони) | ФИО | уточняющий вопрос про ФИО | список активных броней |
| **cancel** (отмена) | ФИО + (модель/город/дата — частично) | если найдено 0 — просьба уточнить; если больше 1 — просьба сузить | Guard Rail-подтверждение → отмена |
| **regulation** (вопрос по регламенту) | сам текст вопроса | явное «не нашёл информации», если документы не дают ответа | ответ на основе документов |

Полная карта с деталями — раздел 4 в `architecture-overview.md`, обоснование конкретных решений по каждому намерению — `ADR-011`, `ADR-016`, `ADR-019`.

---

## Tool Calling (вызов инструментов)

**Что это.** Способность AI-системы не просто отвечать текстом, а самостоятельно вызывать внешние функции/API для получения реальных данных или выполнения действий — например, «посмотреть в базе данных, какие машины свободны» вместо того, чтобы придумывать ответ.

**Где в проекте.** Каждое действие бота, требующее реальных данных, реализовано как вызов внешней функции (RPC) к базе данных: проверка доступности машин, само бронирование, поиск и отмена брони, просмотр списка броней сотрудника. Всего 8 таких функций-инструментов, каждая описана в `api-contract.md` — с параметрами, что возвращает, и что происходит в нештатных случаях.

*\[Скриншот-кандидат: граф pipeline в Dify с несколькими HTTP-узлами, вызывающими RPC — наглядно показывает Tool Calling в действии\]*

## Guardrails (защитные ограничения)

**Что это.** Явные правила, запрещающие AI-модели делать определённые вещи — придумывать факты, принимать решения, которые должны приниматься человеком или системой, выходить за рамки своей роли.

**Где в проекте.** Реализовано на нескольких уровнях:

- **Запрет придумывать факты** — модель, отвечающая на вопросы по регламентам, инструктирована отвечать только на основе реальных документов и явно говорить «не знаю», если ответа в документах нет — вместо того чтобы генерировать правдоподобный, но выдуманный ответ.
- **Запрет модели принимать решение о бронировании самостоятельно** — модель может подготовить данные для бронирования, но реальное действие (запись в базу данных) происходит только после того, как: (а) все данные проверены кодом, а не только «понятны» модели, и (б) пользователь явно подтвердил действие через отдельный шаг проверки (Guard Rail).
- **Валидация вывода модели кодом** — на каждом шаге, где модель определяет, что делать дальше, её ответ дополнительно проверяется программным кодом на соответствие ограниченному списку допустимых вариантов; если модель ответила что-то неожиданное — система не «доверяет ей на слово», а использует безопасное значение по умолчанию.

`ADR-002`, `ADR-025`, раздел 6 в `architecture-overview.md`.

## Source of Truth (источник истины)

**Что это.** Определение того, какие данные в системе считаются «настоящими» и окончательными — то, на что должны ориентироваться все остальные части системы, а не выдумывать заново.

**Где в проекте.** Источником истины является база данных (Supabase/PostgreSQL) — не память диалога, не предположения AI-модели. Явно определено:

- **Что решает модель самостоятельно** — понимание намерения пользователя, формулировка ответа на естественном языке.
- **Что модель обязана передавать во внешнюю систему, не решая сама** — любая проверка реальной доступности машины, любое изменение данных о бронировании (создание, отмена) — всегда идёт через запрос к базе данных, модель не имеет права «решить», что машина свободна, без реальной проверки.
- **Что модель обязана уточнять у пользователя** — недостающие обязательные данные (город, дата, ФИО) — вместо того чтобы додумывать их.
- **На какие вопросы модель не имеет права отвечать без обращения к корпоративным данным** — любой вопрос о конкретных регламентных нормах (лимиты, сроки, правила) — ответ строится только на реальных документах, не на общих знаниях модели.

Раздел «Разбор промпта <5>» и вся ветка защиты от галлюцинаций в RAG (порог релевантности, explicit-проверка пустого результата) — прямая реализация этого принципа.

## Отказоустойчивость

**Что это.** Способность системы продолжать корректно работать (или хотя бы не «падать» без ответа) при сбоях — например, если внешний сервис временно недоступен.

**Где в проекте.** Каждый из вызовов к базе данных снабжён отдельной веткой на случай сбоя — если база данных временно недоступна, пользователь получает понятное сообщение («попробуйте через пару минут»), а не молчание или техническую ошибку. Отдельно предусмотрена защита от гонки условий при одновременных запросах (два сотрудника одновременно пытаются забронировать одну машину) — на уровне базы данных гарантированно не возникнет конфликта. `ADR-009`, `ADR-022`.

---

## Безопасность

**Что это.** Меры защиты данных и системы от несанкционированного доступа или использования.

**Где в проекте.**

- **Row Level Security** — на уровне базы данных включена защита, ограничивающая прямой доступ к таблицам для неавторизованных ролей, даже если такой доступ теоретически станет возможен в будущем (например, при утечке публичного ключа) — `ADR-021`.
- **Разделение прав доступа** — рабочие функции системы выполняются с чётко ограниченными правами, отдельными от прав на прямое изменение структуры данных.
- **Журнал аудита** — фиксируется, кто, когда и какие данные запрашивал или изменял, включая неудачные попытки — `ADR-023`.
- **Секреты** (ключи доступа к базе данных) хранятся в защищённом хранилище платформы, не встроены в код напрямую.

## Эксплуатация системы

### Логирование

**Что это.** Запись того, что происходит в системе, для последующего анализа.

**Где в проекте.** Отдельная таблица журнала событий (`audit_log`), фиксирующая и изменения данных (кто что забронировал/отменил), и обращения на чтение (кто что запрашивал) — реализовано двумя разными механизмами, потому что технически это две разные по сложности задачи. `ADR-023`.

### Мониторинг

**Что это.** Постоянное наблюдение за состоянием системы для своевременного обнаружения проблем.

**Где в проекте.** Журнал аудита фиксирует не только успешные операции, но и сбои (с текстом ошибки) — это основа для последующего мониторинга. Отдельный сервис мониторинга не подключался (не требовалось для масштаба проекта), но структура данных для него подготовлена.

### Трассировка

**Что это.** Возможность проследить полный путь одного запроса через все части системы — что было вызвано, в каком порядке, с каким результатом.

**Где в проекте.** Каждый вызов внешней функции логируется отдельно с результатом (сколько данных найдено, успешно ли выполнено действие), что позволяет восстановить полную последовательность действий пользователя — вплоть до сценария расследования (например: «сотрудник запросил список машин → получил список → отменил чужую бронь → создал новую на другого человека» — такая последовательность полностью видна в журнале).

### Обработка ошибок API

**Что это.** Что происходит, если внешний сервис (API), к которому обращается система, отвечает с ошибкой или не отвечает вовсе.

**Где в проекте.** См. «Отказоустойчивость» выше — каждый вызов внешней функции имеет отдельный путь обработки сбоя.

### Тестовые сценарии

**Что это.** Заранее продуманные и записанные проверки того, что система ведёт себя правильно в разных ситуациях — как в обычных, так и в нестандартных.

**Где в проекте.** `test-plan.md` — свод тестов, включающий больше 50 сценариев: обычные пути использования, пограничные случаи (пустые результаты, неоднозначные запросы, опечатки), проверка правильной работы после смены намерения на середине разговора, проверка сбоев инфраструктуры.

## Prompt Engineering

**Что это.** Искусство формулировать инструкции для AI-модели так, чтобы получать надёжный, предсказуемый и качественный результат.

**Где в проекте.** Множественные примеры по ходу проекта — в том числе задокументированные итерации, когда первая версия инструкции работала ненадёжно, и потребовалось её усилить (например, явное указание «если сомневаешься — выбирай безопасный вариант», запрет домысливать данные, требование не путать смежные темы). Каждая значимая корректировка инструкций для модели зафиксирована в соответствующем ADR.

---

## RAG (Retrieval-Augmented Generation)

**Что это.** Подход, при котором AI-модель отвечает не «из головы», а сначала находит релевантные фрагменты в реальных документах, и уже на их основе формулирует ответ.

**Где в проекте.** Ветка ответов на вопросы по регламентам командировок/отпусков — полноценная реализация RAG с настройкой порога релевантности поиска и защитой от ответа при отсутствии релевантной информации.

---

## Архитектура агентов / Tools

**Что это.** Общий подход к построению AI-системы, где модель не просто ведёт диалог, а способна использовать внешние инструменты (базы данных, API) и принимать решения о том, какой инструмент когда вызвать.

**Где в проекте.** Вся ветка бронирования машин — это агентная система: модель определяет намерение пользователя, извлекает нужные параметры, а специализированные инструменты (RPC-функции) выполняют реальные действия — проверку данных, запись в базу, атомарные транзакции. Полная схема — `architecture-overview.md`.

## Матрица ответственности LLM / API

**Что это.** Явное разделение — что решает языковая модель, а что обязательно должно проверяться или выполняться внешней системой (кодом, базой данных), даже если модель «уверена» в своём ответе.

**Где в проекте.**

| Задача | Кто выполняет | Почему |
|----|----|----|
| Понять намерение пользователя | LLM | Требует понимания естественного языка |
| Извлечь параметры из текста (город, дата, модель) | LLM | Требует понимания естественного языка |
| Проверить, что вывод модели входит в список допустимых значений | Код | Модель может ошибиться или ответить неожиданно — нужна гарантия |
| Проверить реальную доступность машины | База данных | Источник истины — не мнение модели |
| Выполнить бронирование/отмену | База данных (через транзакцию) | Требует гарантии от одновременных конфликтующих действий, которую не может дать LLM |
| Сформулировать понятный ответ пользователю | LLM | Требует естественной речи |
| Решить, показывать ли ответ, или сказать «не знаю» | Код (проверка до вызова LLM) | Нельзя полагаться на то, что модель сама честно откажется отвечать |

Это разделение — сквозной принцип всего проекта, а не отдельная фича; примеры реализации разбросаны по всем разделам `architecture-overview.md`.
