# API-контракт: RPC-функции Supabase

*Последняя актуализация: после введения RLS, advisory lock в reserve_available_car, и параметра p_number в find_booking_to_cancel.*

Это описание всех серверных функций (RPC), которые Dify-бот дёргает через Supabase. Если будете что-то менять в SQL — не забудьте поправить и этот документ, иначе он быстро разойдётся с реальностью (как уже один раз случилось).

Все функции вызываются одинаково:

`POST https://<SUPABASE_URL>/rpc/<function_name>`.

**Обязательные заголовки для всех запросов:** 

`apikey: <SUPABASE_SERVICE_KEY>`
` Authorization: Bearer <SUPABASE_SERVICE_KEY>`
` Content-Type: application/json`  

**Про безопасность**: доступ идёт исключительно через `service_role` ключ — он игнорирует RLS по определению, так что все функции по факту работают с полными правами. RLS на таблицах включён (см. ADR-021), но защищает только гипотетический прямой доступ через `anon`-ключ, не влияет на работу бота.

## get_available_models

Показывает, какие модели машин свободны в городе на дату, и сколько экземпляров каждой.

**Где используется:** первый шаг ветки reserve — прежде чем что-то бронировать, показываем список.

**Параметры:**

| Имя | Тип | Обязателен | Что это |
|----|----|----|----|
| `p_city` | `city_enum` | да | `'Москва'` / `'Санкт-Петербург'` / `'Уфа'` |
| `p_date` | `date` | да | `YYYY-MM-DD` |

**Возвращает:** массив `{model, available_count}`.

**Пример:**

```json
// запрос
{"p_city": "Уфа", "p_date": "2026-08-30"}

// ответ
[
  {"model": "Renault Logan", "available_count": 1},
  {"model": "Toyota Camry", "available_count": 2}
]
```

**Если ничего нет** — пустой массив, это нормальный ответ, не ошибка.

## get_one_available_car

Находит одну свободную машину конкретной модели. **В боевом pipeline не используется** — оставлена в базе как справочная, вместо неё бронирование идёт через `reserve_available_car` (она атомарная, эта — нет, см. предупреждение ниже).

**Параметры:** `p_city`, `p_date`, `p_model` — все обязательны.

**Возвращает:** 0 или 1 строку `{car_id, number, model}`.

⚠️ Не атомарна — между вызовом этой функции и последующим действием ничего не блокируется. Не использовать для реального бронирования, только для предпросмотра.

## reserve_available_car

Главная функция бронирования. Находит свободную машину нужной модели и сразу создаёт бронь — всё в одной транзакции, так что два одновременных запроса не смогут ухватить одну и ту же машину.

**Где используется:** финальный шаг reserve, после того как пользователь выбрал модель и назвал своё ФИО.

**Параметры:**

| Имя | Тип | Обязателен | Что это |
|----|----|----|----|
| `p_city` | `city_enum` | да | Город |
| `p_date` | `date` | да | Дата |
| `p_model` | `text` | да | Модель |
| `p_user_name` | `text` | да | ФИО, точное совпадение с `users.name` |

**Возвращает:** одну строку `{success, message, model, number}`.

**Возможные** `message`:

| Текст | Когда |
|----|----|
| `Успешно забронировано` | всё получилось |
| `Сотрудник не найден` | нет такого `p_user_name` в `users` |
| `Нет свободных машин этой модели на дату` | всё занято или таких машин нет вообще |
| `У сотрудника уже есть бронь в этом городе на эту дату` | сработало бизнес-правило "одна бронь на город/дату на человека" |

**Как устроена защита от гонки:** функция берёт `pg_advisory_xact_lock` по ключу (сотрудник+город+дата) — пока один запрос не завершится, второй такой же от того же человека просто ждёт своей очереди, а не проходит проверку параллельно. Плюс обычный `FOR UPDATE SKIP LOCKED` при выборе конкретной машины среди нескольких одной модели.

**Пример:**

```json
// запрос
{"p_city": "Уфа", "p_date": "2026-08-30", "p_model": "Renault Logan", "p_user_name": "Иванов И.И."}

// ответ
[{"success": true, "message": "Успешно забронировано", "model": "Renault Logan", "number": "C505ET102"}]
```

## get_user_active_bookings

Список действующих броней сотрудника — всё, что подтверждено и ещё не прошло по дате.

**Где используется:** ветка my_bookings.

**Параметры:** `p_user_name` — обязателен, точное совпадение.

**Возвращает:** массив `{booking_id, model, number, city, booking_date}`, отсортировано по дате.

Брони с датой в прошлом или статусом `cancelled` сюда не попадают — не нужно фильтровать по месяцу отдельно, функция уже смотрит вперёд от сегодняшнего дня.

## find_booking_to_cancel

Ищет активные брони сотрудника, можно сужать по модели/городу/дате/номеру машины.

**Где используется:** ветка cancel, шаг поиска нужной брони перед отменой.

**Параметры:**

| Имя | Тип | Обязателен | Что это |
|----|----|----|----|
| `p_user_name` | `text` | да | ФИО |
| `p_model` | `text` | нет (`null`) | Модель |
| `p_city` | `city_enum` | нет (`null`) | Город |
| `p_date` | `date` | нет (`null`) | Дата |
| `p_number` | `text` | нет (`null`) | Госномер машины |

`p_number` добавлен позже — понадобился на случай, когда у сотрудника несколько похожих броней и различить их можно только по номеру машины. На практике такое почти исключено благодаря бизнес-правилу "одна бронь на город/дату" (см. `reserve_available_car`), но параметр оставлен как подстраховка.

**Возвращает:** массив (та же структура, что у `get_user_active_bookings`, плюс `number` уже был там).

**Как читать результат:**

- 0 строк → бронь не найдена, просим уточнить данные.
- 1 строка → можно смело идти на `cancel_booking`.
- больше 1 → нужно доуточнение (обычно такое означает, что параметров дали мало).

**Пример:**

```json
{"p_user_name": "Иванов И.И.", "p_model": null, "p_city": "Уфа", "p_date": null, "p_number": null}
```

⚠️ Опциональные поля обязательно передавать как `null`, а не как пустую строку `""` — иначе `p_city` (это enum) упадёт с ошибкой приведения типа.

## cancel_booking

Отменяет одну конкретную бронь.

**Где используется:** финальный шаг cancel, когда бронь уже однозначно найдена.

**Параметры:** `p_booking_id` — обязателен.

**Возвращает:** `[{"cancelled": true}]`, если реально что-то поменялось; пустой массив, если брони с таким id не было или она уже отменена.

Повторный вызов с тем же id не сломает ничего (второй раз просто вернёт пустоту), но и не сообщит явно "уже отменено" — с точки зрения ответа это неотличимо от "id не найден вообще".

## expire_past_bookings

Служебная — переводит все просроченные (дата в прошлом), но всё ещё числящиеся `confirmed` брони в `cancelled`. В pipeline не вызывается автоматически, только вручную по мере надобности (или можно повесить на `pg_cron`, если понадобится — не настроено).

**Параметры:** нет.

**Возвращает:** `[{"expired_count": N}]`.

Не критична для корректности ответов бота — `get_user_active_bookings` и `find_booking_to_cancel` сами фильтруют по дате независимо от этой функции. Это скорее для порядка в данных, чтобы не копились "живые" брони на прошедшие даты.



## log_read_event

Служебная функция — записывает событие обращения на чтение в таблицу `audit_log`. Не вызывается напрямую пользовательским сценарием; используется как дополнительный шаг после каждого из трёх read-RPC (`get_available_models`, `get_user_active_bookings`, `find_booking_to_cancel`), как на успешном пути, так и при сбое самого read-запроса.

**Где используется:** сразу после <53>/<31>/<38> (успех или fail-ветка) — фиксирует факт и результат обращения к данным.

### Параметры

| Имя | Тип | Обязательный | Описание |
|----|----|----|----|
| `p_action` | `text` | Да | Идентификатор события: `search_available_models`, `search_own_bookings` или `search_booking_to_cancel` |
| `p_details` | `jsonb` | Да | Контекст запроса и его результат (см. примеры ниже) |

### Возвращает

Массив из одного объекта:

| Поле | Тип | Описание |
|----|----|----|
| `logged` | `boolean` | Всегда `true` при успешной записи |

### Формат `p_details` по типам событий

**search_available_models (успех):**

```json
{"city": "Уфа", "date": "2026-08-30", "result_count": 4, "success": true}
```

**search_own_bookings (успех):**

```json
{"employee_name": "Иванов И.И.", "result_count": 3, "success": true}
```

**search_booking_to_cancel (успех):**

```json
{"employee_name": "Иванов И.И.", "city": "Уфа", "model": "Skoda Octavia", "booking_date": "2026-09-05", "result_count": 1, "success": true}
```

**Любое из событий при сбое исходного read-запроса:**

```json
{"city": "Уфа", "date": "2026-08-30", "success": false, "error": "<текст error_message>"}
```

(набор полей контекста соответствует тому же событию, `result_count` отсутствует, добавляются `success: false` и `error`)

### Пример запроса

```json
{
  "p_action": "search_available_models",
  "p_details": {"city": "Уфа", "date": "2026-08-30", "result_count": 4, "success": true}
}
```

### Пример ответа

```json
[{"logged": true}]
```

### Edge cases

- Сбой самой записи лога (например, недоступность Supabase в момент вызова `log_read_event`) обрабатывается через Default Value на HTTP-узле — не прерывает основной пользовательский сценарий, лог в этом случае просто не пишется.
- `actor` не передаётся как параметр — заполняется автоматически значением по умолчанию `'HR_test'` на уровне таблицы `audit_log` (см. ADR-023, авторизация в системе не реализована).
- Функция объявлена с `SECURITY DEFINER` — доступна через `service_role`, RLS на `audit_log` (запрет INSERT для `anon`/`authenticated`) её не затрагивает.
